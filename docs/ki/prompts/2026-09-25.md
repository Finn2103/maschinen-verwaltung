## 1. Fehlersuche in der eigenen Nutzwertanalyse

**Aufgabe**
Die Nutzwertanalyse zur Programmiersprache sollte vor der Entscheidung geprüft werden.

**Prompt**
Die eigene Excel-Tabelle wurde übergeben mit der Aufgabe, sie nach Markdown zu überführen
und dabei Auffälligkeiten zu melden, ohne Zahlen zu verändern.

**Ergebnis**
Drei Befunde: die Gewichte summierten auf 1,10 statt 1,00, JavaScript hatte bei „Typen aus
dem Datenbankschema ableitbar" die Höchstpunktzahl, und ein Ausschlusskriterium war doppelt
benannt.

**Bewertung**
Alle drei übernommen, sie waren nachprüfbar richtig. Wichtig war die Anweisung, **nichts
stillschweigend zu korrigieren**, sondern die Fehler zu melden. So bleiben die Zahlen die
eigenen, und die Korrektur ist eine Entscheidung des Teams und nicht des Werkzeugs.

## 2. Bewertung außerhalb der Skala

**Aufgabe**
Festlegen, welche Punktzahl JavaScript bei „Typen aus dem Datenbankschema ableitbar"
bekommt, nachdem klar war, dass die 5 falsch ist.

**Prompt**
Vorgabe des Teams: **0 Punkte**, weil JavaScript keine Typen besitzt.

**Ergebnis**
Einspruch: die Skala des Blattes reicht von 1 bis 5, eine 0 liegt außerhalb. Vorgeschlagen
wurden zwei Wege, entweder die Skala konsistent auf 0 bis 5 erweitern und das begründen,
oder den kleinsten Wert der Skala nehmen.

**Bewertung**
Einspruch angenommen, JavaScript bekommt **1 Punkt**. Inhaltlich war die Vorgabe richtig,
methodisch nicht. Das Ergebnis ändert sich dadurch nicht: JavaScript fällt so oder so von
Platz 2 auf Platz 3.

## 3. Begründung, die der eigenen Tabelle widerspricht

**Aufgabe**
Die Abweichung von der Rangfolge bei der Linux-Distribution begründen. Die Analyse gewinnt
Ubuntu 26.04, entschieden war Debian 13.

**Prompt**
Als Begründung angeboten: im Team kennt eine Person Linux, und wir kennen Debian. Frage,
ob dafür etwas an der Analyse angepasst werden muss.

**Ergebnis**
Widerspruch mit Rechnung: das Kriterium „Vorkenntnisse im Team" war in der eigenen Tabelle
**zugunsten von Ubuntu** bewertet (3 gegen 2). Das Argument sprach damit gegen die eigene
Entscheidung. Damit Debian allein über dieses Kriterium gewinnt, hätte sein Gewicht von 5
auf 45 steigen müssen und wäre das schwerste Kriterium überhaupt geworden.

**Bewertung**
Übernommen, aber anders als vorgeschlagen aufgelöst. Nicht das Gewicht wurde geändert,
sondern die **Bewertung korrigiert**, denn sie war schlicht falsch herum eingetragen. Die
Entscheidung für Debian steht seitdem auf einer Projektbegründung statt auf einer Zahl.
Zusätzlich wurde in das ADR geschrieben, **was die Begründung nicht behauptet**.

Der Hinweis war unangenehm, aber richtig. Eine Gewichtung so lange zu verschieben, bis das
gewünschte Ergebnis herauskommt, wäre im Fachgespräch die erste Rückfrage gewesen.

## 4. Annahmen der Analyse extern prüfen

**Aufgabe**
Zwei Bewertungen der Linux-Analyse überprüfen, bevor die Abweichung festgeschrieben wird.

**Prompt**
Auftrag, im Netz nachzusehen, ob STRATO überhaupt ein Image für Ubuntu 26.04 anbietet und
ob Ubuntu im Berufsalltag tatsächlich verbreiteter ist als Debian.

**Ergebnis**
STRATO führt Ubuntu 26.04 nur für eine Serverklasse, Debian 13 über mehrere. Bei der
Verbreitung auf Webservern liegt Ubuntu bei 15,1 %, Debian bei 5,8 %.

**Bewertung**
Beide Ergebnisse **bestätigen die eigenen Bewertungen**, keine musste geändert werden. Mit
Quelle und Datum ins ADR übernommen. Eine geprüfte Annahme trägt im Review weiter als eine
ungeprüfte, auch und gerade wenn die Prüfung nichts ändert.
